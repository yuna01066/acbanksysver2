# 근태·연차·휴가 통합 구현 및 운영 적용 안내

## 작업 기준과 범위

- 작업 브랜치: `codex/attendance-leave-hub`
- 기준 커밋: `7347e7b5b64dff1f26d0a6ad4ed3ba33ab0e74d3` (직원별 연차 사용 기록).
- 원격 브랜치와 이전 Lovable 배포 보고를 확인한 뒤 별도 worktree에서 작업했다. 원래 작업 폴더의 변경은 섞지 않았다.
- 실제 배포 서버의 전체 소스 동일성, 운영 DB 마이그레이션 이력과 직원별 잔액은 이번 구현에서 재검증하지 않았다. 배포 전에 아래 절차로 확인해야 한다.
- 이번 작업은 코드·테스트·추가 SQL 작성이다. 운영 DB 변경, 실제 직원 기록 생성/취소/삭제, 커밋, 푸시, Publish는 하지 않았다.

## 구현 내용

`/attendance`의 기본 진입은 내 관리다. 권한 있는 사용자만 관리자 모드로 전환한다.

| 모드 | 메뉴 | 연결 내용 |
| --- | --- | --- |
| 내 관리 | 근태 | 본인 출퇴근·월간 기록·정정 신청·철회·처리 결과 |
| 내 관리 | 연차·휴가 | 공통 잔액·신청·사용/예정 기록·취소 요청·산정 상세 |
| 관리자 | 운영 현황 | 목록/캘린더·월별 미퇴근·날짜별 출근 확인·승인 휴가 |
| 관리자 | 승인함 | 휴가 신청·취소·근태 정정, 알림 요청 직접 열기 |
| 관리자 | 구성원 | 검색·부서·모바일 상세·연도별 사용/전체 신청·근태·부여/차감 |
| 관리자 | 리포트 | 기존 월별 근태·초과근무·부서 분석 |
| 관리자 중 admin만 | 설정 | 연차 정책·휴가 종류·촉진·회사 휴일 |

- 기존 휴가 RPC와 React Query를 재사용했다. 개인 화면에서는 관리자 계정도 본인만 조회한다.
- 승인/취소/정정/조정 후 공통 query invalidation으로 잔액·상세·목록·캘린더·리포트를 갱신한다.
- 과거 휴가/취소/조정 내역을 페이지 단위로 모두 조회하여 응답 건수 제한으로 잔액이 누락되지 않게 했다.
- 기존 개인 계산 함수 5개의 본문은 기준 커밋과 동일하다. 개인 산정 기준을 관리자·마이페이지에 공통 적용했다. 현재 잔액과 선택 연도 기록은 분리했다.
- 기존 소멸·부여 방식은 유지했다. 연도별 원장, 법정 산식 재설계, 과거 데이터 보정은 하지 않았다.
- `/leave-management`, 이전 관리자/리포트 링크, 알림, 직원 프로필 관리 버튼을 통합 페이지에 연결했다.
- 회사 설정의 휴일·연차 탭은 통합 설정 바로가기로 정리했다. 회사정보/GPS·급여·계약·평가·기존 마스터 인증은 변경하지 않았다.
- 중복 대형 대시보드/중첩 관리 탭을 제거하고 기존 UI 토큰·컴포넌트를 재사용했다.

- 승인 사용자/역할, 신청자·날짜·연결 기록, 시간 순서, 대기 상태를 서버에서 검증한다.

- 기존 근태/휴가/취소/조정/정책 행의 ID·일수·상태·승인 이력을 일괄 변경하지 않는다.
- 새로운 Edge Function이나 기존 함수 배포는 필요 없다.

## 운영 반영 게이트

1. Git 원격·배포 커밋·작업 브랜치와 대상 `zwloyqcwyfkimwkohpnd`를 확인한다. 다른 프로젝트 ref, 알 수 없는 pending migration, 기준 불일치 시 중단한다. 기존 폴더의 Supabase CLI 링크 상태를 신뢰하지 않는다.
2. 백업/복구 가능 여부를 확인하고, 같은 시점의 직원·정책·휴가·취소·조정 데이터를 읽기 전용으로 확보한다. 행수/ID/상태/일수 집계와 직원별 기존 개인 잔액 대사 결과를 보관한다. 민감 HR 원본은 Git/일반 보고서에 넣지 않는다.
3. 공통 산식으로 같은 입력을 계산해 비교한다. 기존 관리자/마이페이지에서 소멸 미반영으로 달랐던 표시와 조회 상한 보완 차이는 원인을 기록한다. 설명되지 않는 차이는 자동 보정하지 말고 중단한다.
4. 기존 정정 테이블·trigger·FK·근태 unique(user_id,date)·updated_at trigger·회사 휴일 및 정책 RLS를 확인하고, 검증 환경에서 새 마이그레이션을 먼저 적용한다. 기존 마이그레이션은 수정/재실행하지 않는다.
5. 운영 적용 승인 후 새 마이그레이션을 적용하고 Supabase 타입을 재생성한다. 운영 row/ID/일수/상태가 유지되고 직접 상태 변조가 거부되는지 읽기 위주로 확인한다.
6. RPC 호환 프론트엔드를 배포한다. 구버전 열린 탭은 정정 직접 쓰기가 차단되므로 유지보수 안내와 강제 새로고침 안내를 함께 준비한다. 기존 프론트엔드만 되돌리는 롤백은 정정 기능을 복구하지 못한다.
7. 일반 직원·중간관리자·관리자로 실제 로그인해 본인 조회/타인 차단/정책 권한/모바일/알림 링크를 검증한다. 실제 직원 쓰기 테스트는 별도 승인 후 정확히 특정한 대상에만 수행한다.

문제 시 새 UI 진입을 중지하거나 RPC 호환 직전 빌드로 되돌린다. 이력 삭제, 과거 잔액 재계산, 직접 쓰기 권한의 무조건 복원은 롤백 수단으로 사용하지 않는다.
